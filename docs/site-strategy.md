# サイト方針転換：デモ陳列型 → 課題記事 × 無料ツール × リード獲得型

併せて Instagram / X / note / LinkedIn / LINE の役割分担を設計する（セクション4）。

最終更新: 2026-09-22 / ステータス: 設計（未実装）

## 0. 結論

実現可能。新規開発が必要なのは実質「銀行提出用 計画表」1本と、共通ゲート機構だけ。
出店シミュレーションは `/opening-simulator/` に既にあり（5年PL・損益分岐・投資回収・Excel 4シート出力）、
ゲート追加と記事導線の接続で足りる。

ただし設計上、先に受け入れるべき前提が3つある。

### 前提1: 「メール登録を必須」は静的サイトでは強制できない（確信度: 高）

GitHub Pages に配信ロジックを置けないため、JS で掛けるゲートは DevTools で回避できる。
これは技術的欠陥ではなく、割り切るべき仕様。KPI は「漏れの少なさ」ではなく「月あたりの有効リード数」。
飲食店オーナーが開発者ツールを開いてゲートを抜ける確率は実務上ほぼゼロ。

厳格に守りたい場合はサーバ側で出力を生成する必要があり（Cloudflare Workers 等）、
コストと運用負荷に対してリターンが見合わない。

### 前提2: ゲートで取ったメアドは、それ自体では契約に繋がらない（確信度: 高）

本設計の要点はゲートではなく、その次の一手にある。
このツールの出力は「その人固有の数字が入った、出店計画・銀行提出用の計画表」なので、
「出した計画表を1回無料でレビューします」という提案が極めて自然かつ強い。

したがって価値ラダーを3段で設計し、Tier2（無料レビュー）を
ツール出力画面・自動返信メール・LINE自動応答の3箇所に埋め込む。ここが契約導線の本体。

### 前提3: いま最も効いていない資産はブログ（確信度: 高）

`/blog/` は `assets/blog.json` から note 記事へのリンクを並べるだけで、自社サイトに文章が1本もない。
検索流入・滞在時間・ツールへの内部リンクが全部 note 側に溜まっている。
記事本体を自社サイトに持つことが、この転換で最大のリターンを生む。

## 1. 価値ラダー（ゲート設計の中核）

| 段 | 渡すもの | 対価 | 実装 |
|---|---|---|---|
| Tier 0 | ツールを触る・自分の数字を入れる・画面で結果を見る | なし | 完全開放 |
| Tier 1 | Excel/PDF 出力、保存URL、銀行提出用フォーマット一式、テンプレート | LINE友だち追加 or メール登録 | `assets/gate.js` |
| Tier 2 | 出力した計画表の 30分 無料レビュー（Google Meet） | 名前・店舗名・電話 | フォーム＋カレンダー |
| Tier 3 | 契約 | — | — |

**ゲートは「入口」ではなく「持ち帰り」に掛ける。**
価値を体験し終えた直後に登録を求めるので、登録率が高く離脱が少ない。
入口ゲート（体験ゼロで個人情報を要求）は記事流入で特に効きが悪い。

測るべき比率:
記事→ツール / ツール実行→ゲート表示 / ゲート表示→解除 / 解除→レビュー申込

## 2. 情報設計（サイト構造）

```
/                        トップ = 課題起点のLP
                         ├ ヒーロー: 「どの悩みですか？」課題入口 3〜4
                         ├ 無料ツール 3〜4本   ← 最上位に格上げ（新セクション）
                         ├ 最新記事             ← blog.json から（新セクション）
                         ├ 受託実績 → /works/   ← 現 #works を改称・格下げ
                         └ 相談CTA（既存 #cta）

/blog/                   記事一覧（上段=自社ガイド / 下段=noteコラム。混ぜない）
/blog/<slug>/            記事本体（新規）
                         └ 記事末: この課題を解くツール 1つ ＋ 関連記事

/tools/                  無料ツール一覧（ハブ）
/tools/<key>/            ツールごとのLP（現 /tools/?t=xxx を静的化）
/opening-simulator/      出店シミュ（既存・ゲート追加）
/bank-plan/              銀行提出用 事業計画表（新規）
/works/                  受託実績（店舗固有デモを集約）

/assets/gate.js          共通ゲート（モーダル・localStorage・GAS送信・LINEコード照合）
/assets/gate.css
/assets/leads.gs         Apps Script ソース（デプロイ用・リポジトリ保管）
/content/posts/*.md      記事原稿（Markdown）
/tools/build_blog.py     Markdown → HTML 生成（GitHub Actions で実行）
```

既存URLは壊さない。`/tools/?t=opening` は `/tools/opening/` へ JS リダイレクト
（GitHub Pages に 301 はないため / 確信度: 高）。

**1記事 = 1課題 = 1ツール。** 記事末に複数のツールを並べると選べず離脱する。

## 3. ゲートの技術設計

### 3-1. UI

出力ボタンを押した瞬間にモーダル。2タブ。

**タブA: LINEで受け取る（デフォルト表示）**

1. 友だち追加ボタン（`SITE_CONFIG.lineUrl` = `https://lin.ee/tExiJ9c`）
2. 「LINEで `計画表` と送信してください」
3. キーワード自動応答で解除コードが届く（例 `SD-PLAN-2609`）
4. コードを入力 → 解除

これで**友だち追加を実質的に検証できる**のが利点。
LINE公式アカウントのキーワード応答は無料プランでも使える（確信度: 高）。
応答メッセージは無料メッセージ通数（月200通）にカウントされない（確信度: 中／要確認）。

コードは月替わりローテーション（`SD-PLAN-YYMM`）。照合はクライアント側なので
コードは HTML 内に存在するが、それが落とすのは「コードを知っている = LINEに来た」の
推定精度だけで、ゲートの目的（接点作り）は損なわれない。

**タブB: メールで受け取る**

- 入力: メールアドレス（必須）／店舗名（必須）／業態・席数・出店予定時期（任意）
- POST → Apps Script Webアプリ → スプレッドシート追記 → 自分に通知 → 相手に自動返信
- 自動返信テンプレに Tier2（無料レビュー）の案内を必ず入れる
- 成功レスポンスで解除

### 3-2. 解除状態の保持

```js
localStorage.sd_unlock = { ts: <epoch>, via: "line" | "mail", email?: "..." }
```

**ツール横断で共通。** 1回登録すれば全ツールの出力が開く。
ゲートを何度も出すのは最も嫌われる設計なので、ここは必ず共通化する。

### 3-3. なぜ Formspree ではなく Apps Script か

| | Formspree（現行） | Apps Script |
|---|---|---|
| 無料枠 | 月50件（確信度: 中） | 実質制限なし |
| リードDB | 管理画面／メール | スプレッドシートがそのままDB |
| 自動返信 | 有料プラン寄り | GASで自由に書ける |
| 運用適合 | — | 業務が Google 完結なので自然 |

ゲートが機能した時点で Formspree 無料枠は即上限に当たる。
既存の問い合わせフォーム（`#contactForm`）は件数が少ないので Formspree のまま残して問題ない。

実装上の注意（確信度: 高）:
- GAS Webアプリは「アクセスできるユーザー: 全員」で公開する必要がある
- CORS プリフライトを避けるため `Content-Type: text/plain` で POST し、GAS 側で JSON.parse する
- スプレッドシートの共有は自分のみに制限する

### 3-4. 個人情報の扱い

- `/privacy/` は既にあるので、モーダル内に同意チェック＋ポリシーリンクを置く
- 「営業目的でご連絡する場合があります」を明記する
- 匿名のアクセス解析（GoatCounter・Cookieレス）とリード情報は別物として分けて説明する

## 4. チャネル設計（自社サイト / Instagram / X / note / LinkedIn / LINE）

### 4-0. 前提：この商売で契約が生まれる経路（確信度: 高）

外注として業務に入り込む高信頼・長サイクル型のコンサルなので、契約の発生源はこの順。

1. **紹介**（既存顧客・取引先・同業）← 圧倒的に1位
2. 直接の面識（業界の集まり、現場、展示会）
3. 検索して問い合わせ（数は少ないが意図が明確で確度が高い）
4. SNSで見つけて長期に温まる（最も遅い）

したがって **SNS単体では契約は生まれない。SNSは「紹介」と「検索」を増幅する装置**にすぎない。
ここを取り違えてフォロワー数を追うと、工数を溶かして終わる。

#### 最優先は「裏取りの整備」

紹介が起きた瞬間、相手は必ず名前と社名を検索する。そこで出てくるものが：

- 自社サイト（実績・料金・人柄）← ある
- Instagram（活動が生きているか）← **要**
- 検索結果に記事（この人は分かっているか）← **要**

これが揃っていないと**紹介が途中で死ぬ**。SNSに投資する最大の理由はリーチではなく、ここ。

#### SNS設計より先に効くこと（正直に言うと）

最大の営業資産は既存3クライアント（旬彩坊・ジャパンダイニング・VRtrade）。
**成果を事例化して紹介を依頼する**のが契約への最短距離で、SNSより速く確実。
ただし守秘があるので、事例化には各社の許可取りが前提。SNS運用と並行してここを進めるべき。

### 4-1. チャネルごとの役割・KPI・工数・優先度

| チャネル | 役割（ファネル位置） | ターゲット | 見るKPI | 月工数 | 優先度 |
|---|---|---|---|---|---|
| **自社サイト記事＋ツール** | 獲得・転換 | 検索してきた飲食店・卸 | ゲート解除数／レビュー申込数 | 8〜12h | ★★★ 1 |
| **Instagram** | 裏取り・オーナー層リーチ | 個人店〜数店舗のオーナー | 保存数／プロフィールリンククリック／DM数 | 4〜6h | ★★★ 2 |
| **LINE公式** | 既存リードの維持・再接触 | ツールを使った人 | 配信クリック／レビュー申込 | 1h | ★★ 3 |
| **X** | 業界内認知・ツール配布 | 業界関係者・業界メディア | リンククリック／リポスト | 2〜3h | ★★ 4 |
| note | 人柄・信頼（余力があれば） | 幅広い（飲食以外も多い） | サイトへの遷移数 | 0〜3h | ★ 5 |
| LinkedIn | プロフィールを置くだけ | チェーン本部・大手卸 | — | 0h | ☆ 6（保留） |

工数が月1〜2本の前提では、**薄く6チャネル回すのが最悪**。
絞るなら **自社サイト ＋ Instagram** の2つ。これだけで裏取りと獲得は成立する。

### 4-2. ハブ＆スポーク（1コンテンツを全チャネルに転用）

SNSでオリジナルを作らない。これが工数を現実的にする唯一の方法。

```
サイト記事1本（決定版・2000〜4000字・ストック・ハブ）
  ├→ カルーセル画像10枚に分解 ────→ Instagram（保存される形）
  ├→ 要点を3〜5連投に分解 ────────→ X
  ├→ 記事の背景・現場エピソード ──→ note（書けた月だけ）
  ├→ 更新通知 ───────────────────→ LINE
  └→ 記事末 → ツール → 出力でゲート → リード
```

加えて、低工数で毎日回せるものを1つだけ持つ：
**業界ニュース＋一言コメント → X**。
`.github/scripts/fetch_news.py` で毎日業界ニュースを自動取得する仕組みが既にあるので、
これをXの投稿ネタに転用できる（確信度: 高／仕組みは既に稼働中）。

### 4-3. 自社サイト記事（ハブ）

**役割**: 検索で獲得し、ツールへ転換する。ストック型で、増やすより育てる。

- 検索意図に answer する記事だけを書く（計算方法・手順・公的様式の書き方・判断基準・相場）
- **ツールと1:1。4課題なら4本。** 増やすのではなく更新して育てる
- 1記事1CTA。記事末のツールは1つだけ

**年4本**で足りる。これなら止まらない。

| 課題 | サイト記事（決定版） | ツール |
|---|---|---|
| 出店判断 | 飲食店の出店判断を数字でする方法（売上の積み上げ／損益分岐点／投資回収） | 出店シミュレーション |
| 資金調達 | 銀行・公庫に出す事業計画書の作り方（項目／数値根拠／資金繰り表） | 銀行提出用 計画表（新規） |
| 原価・仕入 | 飲食店の原価率を下げる手順（品目別分析／相見積の取り方／効果測定） | 仕入れ見える化レポート |
| 数字管理 | 飲食店の月次で見るべき数字（指標の定義とベンチマーク） | 月次業績レポート |

### 4-4. Instagram（最も詰めるべきチャネル）

**役割**: 「裏取り」と、飲食店オーナー層への唯一の濃いリーチ。

飲食店オーナーはInstagramを**自店の集客のために**使っている。経営課題のコンテンツを探しては
いないので、ここは「発信で見つけてもらう場所」ではなく **「会う前に見られる名刺」** として設計する。

構造的な弱点を先に認識する: **Instagramは本文にリンクが貼れない**（プロフィールリンク1つのみ）。
ツール導線は作りにくい。だからリーチではなくプロフィールクリックとDMを見る。

#### 固有の強み

Instagram分析ダッシュボードを自作している（`/instagram-analytics/`）。
**自分のアカウントを数字で運用し、その運用結果自体をコンテンツにできる。**
「数字で運用している実演」が、そのまま最強の営業材料になる（確信度: 中〜高）。

#### 投稿の型は3つだけ

1. **数字カルーセル**（保存狙い・週1）
   「原価率の計算」「出店判断の5指標」「公庫に出す数字の作り方」。サイト記事の分解。
2. **ビフォーアフター**（信頼狙い・隔週）
   受託実績の画面。既存の `assets/shot-*.png` がそのまま素材として使える。
3. **顔と現場**（人柄狙い・月1）
   市場・厨房・会議。外注として現場に入っている強みがそのまま出る。noteを切る場合、
   「人柄・信頼」の役はこの型が引き取る。

#### プロフィール

- 一行で何屋か分かる表記（例「飲食店の数字を整える人」）
- **リンクは1つだけ。`/tools/`（無料ツール一覧）に集約。** linktree等を挟むとクリックが落ちる（確信度: 中）
- ハイライトに「無料ツール」「実績」「料金」

#### やらないこと

**フォロワー数を追わない。** 飲食店オーナー数十人に届けば成立する商売なので、
リーチ数ではなくプロフィールクリック・DM・保存を見る（確信度: 高）。

#### 横展開

リールを1本作るなら TikTok / YouTube ショートへの転載はほぼ無料。
ただし新規に動画を企画するのは工数が重いので、**転載以上のことはしない**。

### 4-5. X

**役割**: 業界内の認知と、ツール公開時の配布チャネル。

利点は**リンクが貼れる・速い・X内検索で見つかる**こと。
欠点は流速が速くストックにならないこと、フォロワーの積み上がりが遅いこと。

運用:
- 毎日1ポスト: 業界ニュース＋一言コメント（`fetch_news.py` のネタを転用）
- 週1: サイト記事のスレッド（3〜5連投）＋末尾にリンク
- 月1: ツール公開・更新の告知
- フォローは待たずにこちらから繋ぐ（飲食業界の経営者・業界メディア・フードテック関係者）

### 4-6. note

本人の意向は「最悪切り捨ててよい」。判断: **新規投稿は止めてよいが、アカウントと既存9本は残す。**

- 既存9本は放置してもマイナスにならない。削除は被リンクと検索順位を捨てることになるので損
- 5ヶ月止まっている（最新 2026-04-24／確信度: 高）
- 既存6本は全部「気づき・意見型」で検索型が1本もない。**サイトへの移植はしない**
  （「仕入れ先 変えると怒られる」で検索する人はいない。移植しても検索流入は増えず、note側の順位とカニバる）
- 1回だけやる価値がある作業: **プロフィール欄と既存記事末に `/tools/` へのリンクを追記**。
  サイト記事ができてから、9本分。効果は高く、一度で済む

再開する場合の使い分け:

| | note | 自社サイト |
|---|---|---|
| 読者の状態 | 回遊中。課題認識が曖昧 | 課題を言語化して検索した |
| 記事の役割 | 「なんかおかしい」と気づかせる | 「どう計算するか」を示す |
| 型 | フロー（800〜1500字） | ストック（2000〜4000字） |
| CTA | サイト記事へ1本だけ。売り込まない | ツールへ1つだけ |

判定基準は一つ: **そのタイトルで検索する人がいるか。** いなければnote、いればサイト。

接続ルール:
- note記事は**完結させる**。「続きはサイトで」は禁止（note文化に反する）
- note記事末に「この計算をするツールと手順はこちら」でサイト記事へ1本だけ
- 逆方向（サイト→note）は本文中の控えめな参照1つ。主導線にしない

内容が違うので重複コンテンツ問題と canonical の悩みは消える。

### 4-7. LinkedIn

**判断: 今期はやらない。プロフィールだけ整えて放置。**

理由: **日本の飲食店・卸業界にLinkedInユーザーはほぼいない**（確信度: 高）。
限られた工数を効かない場所に使うべきでない。

ただし条件付きで主戦場になる。LinkedInが効くのは
**大手外食チェーン本部・上場外食企業の経営企画/SCM・食品卸の大企業・投資会社**。

VRtradeでやっている業務（締め作業の自動化、エラー特定、データ管理）は
**「飲食業界に強いDX・データ屋」**として売れる内容で、この層とLinkedInに相性がいい。
つまり LinkedIn をやるかは **顧客層を中小から大手に広げる意思があるか**という事業判断で決まる。
現状の3クライアント構成（中小）を前提にするなら保留が正解（確信度: 中〜高）。

### 4-8. LINE公式

**役割**: Tier1で取得したリードの維持と再接触。新規獲得チャネルではない。

- 配信は月1回程度（無料枠が月200通のため）
- 内容: サイト記事の更新、ツールの追加・改善、季節ネタ（繁忙期前の原価見直し等）
- キーワード自動応答は解除コード配布に使う（3-1参照）
- 配信の目的は Tier2（無料レビュー）への誘導

### 4-9. `/blog/` の表示設計（役割が違うものを混ぜない）

```
/blog/
├ 【上段】課題別ガイド（自社記事・4本程度）
│   カード大きめ。「出店判断」「資金調達」「原価・仕入」「数字管理」
│   各カードに関連ツールのバッジ
│
└ 【下段】コラム（note）
    現在のカードデザインを流用。「noteで書いています」と明記し外部リンクアイコンを付ける
```

`blog.json` のスキーマを**キー分離**に変更する：


## 5. 新規ツール: 銀行に見せる計画表 `/bank-plan/`

### 5-1. 銀行・日本政策金融公庫が実際に見るもの

- 創業計画書の項目: 創業の動機／経営者の略歴／取扱商品・サービス／取引先／必要な資金と調達方法／事業の見通し
- 数値計画: 月次資金繰り表（12ヶ月）／年次PL（3〜5年）／借入返済計画／損益分岐点
- 根拠: 売上の積み上げ（席数 × 回転 × 客単価 × 営業日）、原価率・人件費率の根拠

### 5-2. 出店シミュとの関係

重複 = 売上積み上げ・PL（8割）。
差分 = **月次資金繰り表・返済計画と、「様式に落とした出力」**。

設計判断: **独立URLの別ツールにする。** 理由は記事と検索キーワードが別（出店判断 vs 資金調達）で、
集客入口として分けるべきだから。ただし計算エンジンは共通JS（`assets/plan-core.js`）に切り出して共有する。

出店シミュの入力を `/bank-plan/` に引き継ぐ導線（localStorage 経由）を用意する。
「シミュ結果をそのまま計画表に流し込める」こと自体が Tier1 の価値になる。

### 5-3. 出力（= ゲート対象）

- Excel: 創業計画／資金計画／月次資金繰り／年次PL／返済計画 の5シート
- PDF: 印刷してそのまま持参できる体裁

必須の注記: **「本ツールの出力は融資の可否を保証するものではありません」**

### 5-4. 正直な但し書き（確信度: 中）

公庫の正式様式そのものを再現すると、様式改定への追従コストが毎年かかる。
推奨は「公庫の項目に対応した独自フォーマット」＋「公庫様式への転記用チートシート」。
実装前に最新様式を確認すること。

## 9. リスクと懸念（正直なところ）

1. **執筆が続かないリスクは、構造で下げてある（確信度: 中）**
   サイト記事は年4本のストック型（増やさず育てる）、SNSはハブ&スポークで転用のみ、
   noteは止まっても設計が壊れない（サイト記事は検索から直接入れる）。
   ただし**年4本すら書けないなら、この設計全体が動かない**。
   だから Phase 1 は記事1本＋ツール1本に絞って先に検証する。

2. **無料ツールの品質が低いと逆効果**
   ツールは「この会社に任せて大丈夫か」の判断材料になる。
   既存デモは架空データでは綺麗だが、実際の自店データを入れて破綻しないかの検証が必要。

3. **リードデータが Google Sheets 任せ**
   バックアップ方針とアクセス権を最初に決めておく。

4. **SEO の競合が強い（確信度: 中）**
   出店・融資系キーワードは金融機関・大手メディアが上位を占める。
   勝てるのは「飲食店 × 具体的な状況」のロングテール。
   検索だけを前提にせず、note・LINE・既存顧客経由の流入も導線に織り込む。

5. **SNSをリーチ装置と誤解するリスク（確信度: 高）**
   この商売の契約源は紹介が1位で、SNSは紹介と検索の「裏取り装置」。
   フォロワー数を追い始めた時点で工数が溶ける。KPIはプロフィールクリック・DM・ゲート解除に置く。

6. **既存クライアントの事例化には許可が必要**
   最も速い営業導線（既存3社の成果を事例化して紹介を依頼する）は守秘の制約を受ける。
   SNS設計と並行して各社の許可取りを進める必要がある。

7. **LINE 解除コードの流出**
   記事やSNSに貼られると無効化する。月次ローテーションで寿命を切って割り切る。
