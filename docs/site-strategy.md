# サイト方針転換：デモ陳列型 → 課題記事 × 無料ツール × リード獲得型

最終更新: 2026-09-22 / ステータス: 設計（未実装）

## 0. 結論

実現可能。新規開発が必要なのは実質「銀行提出用 計画表」1本と、共通ゲート機構だけ。
出店シミュレーションは `/opening-simulator/` に既にあり（5年PL・損益分岐・投資回収・Excel 4シート出力）、
ゲート追加と記事導線の接続で足りる。

ただし設計上、先に受け入れるべき前提が3つある。

### 前提1: 「メール登録を必須」は静的サイトでは強制できない（確信度: 高）

GitHub Pages に配信ロジックを置けないため、JS で掛けるゲートは DevTools で回避できる。
これは技術的欠陥ではなく、割り切るべき仕様。KPI は「漏れの少なさ」ではなく「月あたりの有効リード数」。
飲食店オーナーが開発者ツールを開いてゲートを抜ける確率は実務上ほぼゼロ。

厳格に守りたい場合はサーバ側で出力を生成する必要があり（Cloudflare Workers 等）、
コストと運用負荷に対してリターンが見合わない。

### 前提2: ゲートで取ったメアドは、それ自体では契約に繋がらない（確信度: 高）

本設計の要点はゲートではなく、その次の一手にある。
このツールの出力は「その人固有の数字が入った、出店計画・銀行提出用の計画表」なので、
「出した計画表を1回無料でレビューします」という提案が極めて自然かつ強い。

したがって価値ラダーを3段で設計し、Tier2（無料レビュー）を
ツール出力画面・自動返信メール・LINE自動応答の3箇所に埋め込む。ここが契約導線の本体。

### 前提3: いま最も効いていない資産はブログ（確信度: 高）

`/blog/` は `assets/blog.json` から note 記事へのリンクを並べるだけで、自社サイトに文章が1本もない。
検索流入・滞在時間・ツールへの内部リンクが全部 note 側に溜まっている。
記事本体を自社サイトに持つことが、この転換で最大のリターンを生む。

## 1. 価値ラダー（ゲート設計の中核）

| 段 | 渡すもの | 対価 | 実装 |
|---|---|---|---|
| Tier 0 | ツールを触る・自分の数字を入れる・画面で結果を見る | なし | 完全開放 |
| Tier 1 | Excel/PDF 出力、保存URL、銀行提出用フォーマット一式、テンプレート | LINE友だち追加 or メール登録 | `assets/gate.js` |
| Tier 2 | 出力した計画表の 30分 無料レビュー（Google Meet） | 名前・店舗名・電話 | フォーム＋カレンダー |
| Tier 3 | 契約 | — | — |

**ゲートは「入口」ではなく「持ち帰り」に掛ける。**
価値を体験し終えた直後に登録を求めるので、登録率が高く離脱が少ない。
入口ゲート（体験ゼロで個人情報を要求）は記事流入で特に効きが悪い。

測るべき比率:
記事→ツール / ツール実行→ゲート表示 / ゲート表示→解除 / 解除→レビュー申込

/tools/<key>/            ツールごとのLP（現 /tools/?t=xxx を静的化）

**1記事 = 1課題 = 1ツール。** 記事末に複数のツールを並べると選べず離脱する。

## 3. ゲートの技術設計

### 3-1. UI

出力ボタンを押した瞬間にモーダル。2タブ。

**タブA: LINEで受け取る（デフォルト表示）**

1. 友だち追加ボタン（`SITE_CONFIG.lineUrl` = `https://lin.ee/tExiJ9c`）
2. 「LINEで `計画表` と送信してください」
3. キーワード自動応答で解除コードが届く（例 `SD-PLAN-2609`）
4. コードを入力 → 解除

これで**友だち追加を実質的に検証できる**のが利点。
LINE公式アカウントのキーワード応答は無料プランでも使える（確信度: 高）。
応答メッセージは無料メッセージ通数（月200通）にカウントされない（確信度: 中／要確認）。

コードは月替わりローテーション（`SD-PLAN-YYMM`）。照合はクライアント側なので
コードは HTML 内に存在するが、それが落とすのは「コードを知っている = LINEに来た」の
推定精度だけで、ゲートの目的（接点作り）は損なわれない。

**タブB: メールで受け取る**

- 入力: メールアドレス（必須）／店舗名（必須）／業態・席数・出店予定時期（任意）
- POST → Apps Script Webアプリ → スプレッドシート追記 → 自分に通知 → 相手に自動返信
- 自動返信テンプレに Tier2（無料レビュー）の案内を必ず入れる
- 成功レスポンスで解除

### 3-2. 解除状態の保持

```js
localStorage.sd_unlock = { ts: <epoch>, via: "line" | "mail", email?: "..." }
```

**ツール横断で共通。** 1回登録すれば全ツールの出力が開く。
ゲートを何度も出すのは最も嫌われる設計なので、ここは必ず共通化する。

### 3-3. なぜ Formspree ではなく Apps Script か

| | Formspree（現行） | Apps Script |
|---|---|---|
| 無料枠 | 月50件（確信度: 中） | 実質制限なし |
| リードDB | 管理画面／メール | スプレッドシートがそのままDB |
| 自動返信 | 有料プラン寄り | GASで自由に書ける |
| 運用適合 | — | 業務が Google 完結なので自然 |

ゲートが機能した時点で Formspree 無料枠は即上限に当たる。
既存の問い合わせフォーム（`#contactForm`）は件数が少ないので Formspree のまま残して問題ない。

実装上の注意（確信度: 高）:
- GAS Webアプリは「アクセスできるユーザー: 全員」で公開する必要がある
- CORS プリフライトを避けるため `Content-Type: text/plain` で POST し、GAS 側で JSON.parse する
- スプレッドシートの共有は自分のみに制限する

### 3-4. 個人情報の扱い

- `/privacy/` は既にあるので、モーダル内に同意チェック＋ポリシーリンクを置く
- 「営業目的でご連絡する場合があります」を明記する
- 匿名のアクセス解析（GoatCounter・Cookieレス）とリード情報は別物として分けて説明する

## 4. 記事の仕組み（自社サイト主・note クロスポスト）

### 4-1. パイプライン

```
content/posts/2026-09-shutten-marketing.md
   ↓ GitHub Actions（content/ への push で起動）
tools/build_blog.py
   → /blog/<slug>/index.html を生成
   → assets/blog.json に自社記事をマージ（note記事と統合／自社記事を優先表示）
   → sitemap.xml を更新
```

既存の `.github/workflows/note-feed.yml`（毎朝 note RSS → blog.json）はそのまま活かし、
`blog.json` を「自社記事 + note記事」のマージ形式に拡張する。

### 4-2. front matter

```yaml
---
title: 新規出店を考えるとき、マーケティングしてる？
slug: shutten-marketing
date: 2026-09-25
pain: 出店判断
tool: opening-simulator          # 記事末に出すツール（1つだけ）
next: bank-plan                  # 次に読ませる記事/ツール
description: ...
og: /assets/blog/shutten-marketing.png
note_url: https://note.com/spicy_device/n/xxxx
---
```

`tool:` で記事とツールを 1:1 に紐づけるのが設計の核。

### 4-3. note との関係

- 自社サイトを先に公開 → note に転載し、note 記事末に「ツールはこちら」を置く
- note は canonical タグを自由に設定できない（確信度: 中／仕様変更の可能性あり）。
  重複コンテンツのリスクは実務上ほぼ問題にならないが、気になるなら
  「note は冒頭3〜4割＋続きはサイトで」に切り替える

### 4-4. 記事とツールの対応表

既存の note 記事が既にこのラインに4本乗っている。
**最初の作業は新規執筆ではなく、既存 note 記事の自社サイト移植＋ツール接続。** これが一番早い。

| 課題 | 記事 | ツール |
|---|---|---|
| 出店判断 | 新規出店を考えるとき、マーケティングしてる？（新規）<br>飲食店の出店判断、感覚でやっていませんか（note既存） | 出店シミュレーション |
| 資金調達 | 銀行に出した計画書、なぜ通らなかったのか（新規） | 銀行提出用 計画表（新規） |
| 原価・仕入 | 相見積を取っても利益が改善しない店の共通点（note既存）<br>仕入れを見直した。でも良くなったか分からない（note既存） | 仕入れ見える化レポート |
| 数字管理 | 料理もサービスも良いのに利益が残らない（note既存） | 月次業績レポート |

## 5. 新規ツール: 銀行に見せる計画表 `/bank-plan/`

### 5-1. 銀行・日本政策金融公庫が実際に見るもの

- 創業計画書の項目: 創業の動機／経営者の略歴／取扱商品・サービス／取引先／必要な資金と調達方法／事業の見通し
- 数値計画: 月次資金繰り表（12ヶ月）／年次PL（3〜5年）／借入返済計画／損益分岐点
- 根拠: 売上の積み上げ（席数 × 回転 × 客単価 × 営業日）、原価率・人件費率の根拠

### 5-2. 出店シミュとの関係

重複 = 売上積み上げ・PL（8割）。
差分 = **月次資金繰り表・返済計画と、「様式に落とした出力」**。

設計判断: **独立URLの別ツールにする。** 理由は記事と検索キーワードが別（出店判断 vs 資金調達）で、
集客入口として分けるべきだから。ただし計算エンジンは共通JS（`assets/plan-core.js`）に切り出して共有する。

出店シミュの入力を `/bank-plan/` に引き継ぐ導線（localStorage 経由）を用意する。
「シミュ結果をそのまま計画表に流し込める」こと自体が Tier1 の価値になる。

### 5-3. 出力（= ゲート対象）

- Excel: 創業計画／資金計画／月次資金繰り／年次PL／返済計画 の5シート
- PDF: 印刷してそのまま持参できる体裁

必須の注記: **「本ツールの出力は融資の可否を保証するものではありません」**

### 5-4. 正直な但し書き（確信度: 中）

公庫の正式様式そのものを再現すると、様式改定への追従コストが毎年かかる。
推奨は「公庫の項目に対応した独自フォーマット」＋「公庫様式への転記用チートシート」。
実装前に最新様式を確認すること。

## 9. リスクと懸念（正直なところ）

1. **記事を書き続けられるかに全部依存する（確信度: 高）**
   この設計は記事本数に比例してしか効かない。月2本を6ヶ月続けられないなら、
   ゲートを作ってもリードは流れてこない。だから Phase 1 を小さく回して先に検証する。

2. **無料ツールの品質が低いと逆効果**
   ツールは「この会社に任せて大丈夫か」の判断材料になる。
   既存デモは架空データでは綺麗だが、実際の自店データを入れて破綻しないかの検証が必要。

3. **リードデータが Google Sheets 任せ**
   バックアップ方針とアクセス権を最初に決めておく。

4. **SEO の競合が強い（確信度: 中）**
   出店・融資系キーワードは金融機関・大手メディアが上位を占める。
   勝てるのは「飲食店 × 具体的な状況」のロングテール。
   検索だけを前提にせず、note・LINE・既存顧客経由の流入も導線に織り込む。

5. **LINE 解除コードの流出**
   記事やSNSに貼られると無効化する。月次ローテーションで寿命を切って割り切る。

## 10. 決定済み事項

| 論点 | 決定 |
|---|---|
| 記事の置き場 | 自社サイト主・note はクロスポスト |
| ゲート位置 | 出力・持ち帰りのみ（入口は完全開放） |
| リード受け皿 | LINE（キーワード応答で解除コード）＋ メール（GAS → スプレッドシート）併用 |
| 既存デモ | 汎用4本を無料ツールへ昇格、残りは `/works/` に格下げ。URLは維持 |
