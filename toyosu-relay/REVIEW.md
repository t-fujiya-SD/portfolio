## 0. この記録の位置づけ

TOYO LINK の思想を他事業へ横展開できないか検討した結果を、裏取りした上で固定したものです。
検討そのものは別途 ChatGPT と行い、**そのうちコードで検証できる主張・Web で裏が取れる主張だけを残しました。**

確認の結果、ChatGPT のコードに関する断定（CSV の返品控除漏れ、`respMin` のハードコード、締めがブール1個、成立≠履行）は**ほぼすべて事実**でした。実際に公開 HTML を読んだ上での指摘です。**確信度：高**

## 1. 設計パターン（4つ）

TOYO LINK の根っこにある、業種を問わず使える型。

| | パターン | 意味 |
|---|---|---|
| **P1** | 使い慣れた連絡手段を残す | 相手に新しい仕事の仕方を強制しない。電話・FAX・LINE で受け、担当者が必要な結果だけ記録する |
| **P3** | 口頭の合意を双方で確定する | 一方のメモを、当事者間で確認した記録に変える |
| **P6** | 記録を後工程で再利用する | 現場の入力が、事務や管理の仕事も減らす。請求・発注・作業指示・月末照合へ渡す |
| **P7** | 入力した本人にもすぐ利益を返す | 管理者のためだけの記録にしない。再電話・説明のやり直し・未回答の追跡を減らす |

検討段階では7個（P1〜P7）ありましたが、**P2（相談先を広げる）は掲示板そのもの、P4（完了まで追う）は P3 の延長、P5（公開範囲の制御）は運用ルール**であり、思想として独立に立てる必要がないため4つに圧縮しました。

**変えないのは「電話」そのものではなく、「現場が柔軟に判断できること」**です。卸では電話が適していても、別の文脈ではボタン操作の方が適している場合があります。掲示板も月次精算も必須ではありません。

## 2. 「本人はアプリを開かない」という設計反転 ★最重要

TOYO LINK の大前提は「卸業者自身がアプリを開く」ですが、**相手がタノム程度のアプリすら使えない場合、この前提は成立しません。**

そこで前提を反転させます。

> **現場は今までどおり電話・FAX。裏側の担当者（卸の営業・受注事務・集荷担当）だけが業務画面を使い、相手探し・記録・進捗管理を行う。**

つまり作るべきものは、現場向けアプリではなく
**「電話を受けた担当者が、探す・忘れない・引き継ぐための業務画面」**です。

### 裏付け

この形は思いつきではなく、**既に商用で成立している型**です。

- TANOMU の「代理入力」機能：「納品先で口頭で受けた注文や、イレギュラーに電話で受けた注文を、**自社スタッフが TANOMU 上で顧客に代わって発注できる**」
  出典: https://www.infomart.co.jp/tanomu/seller/index.asp

**確信度：高**

### 注意点

電話の内容が勝手に正確な記録になるわけではありません。**最初に「誰が入力し、誰が確認するか」を決める必要があります。** ここを詰めずに始めると、工数が全部こちらに集中します。

## 4. 空いている領域（裏付けあり）

### A. 欠品・代替の「合意」の記録化

業界メディアが「**納品数量が欠品や代替で動いたときの修正をどこで受けるか**が受発注システム選定の重要論点」と明記しているのに、**どの製品も機能化していません。**
TANOMU も クロスオーダー も「欠品の**連絡**」までで、「代替提案 → 相手の合意 → 下流への反映」は公開情報上、確認できませんでした。

出典: https://www.issoh.co.jp/column/details/17138/

**空いているのは3点**
1. 代替提案の構造化（欠品品目 → 候補SKU・規格・産地・単価を並べて提示 → 相手が選ぶ）
2. 合意の証跡（誰が・いつ・どの代替案に・いくらで合意したか）
3. 合意結果の下流への反映（注文数量の書き換え → 納品書 → 請求）

業界は**赤伝で事後処理**しており、事前合意との接続がありません。

**確信度：中〜高**（課題の存在は高、競合不在は「公開情報に見当たらない」という意味）

**戦い方**: TANOMU（飲食店11万軒）／クロスオーダーの**代替**を狙うのは無謀。**既存受発注SaaSの外側で「電話で決まった変更を記録する薄い層」に徹し、CSV／API で戻す**のが現実的。

### B. 現場で起きた返品・不足の記録 → 赤伝データへの受け渡し

- ERP・販売管理層（アラジンオフィス、ASPAC、EXPLANNER/Ax 等）は**赤伝（赤黒処理）として業界標準で実装済み**
- 一方、**飲食店⇄卸の受発注SaaS 層で、返品・不足を現場で記録して請求に反映する機能は確認できず**

現状は **現場 → 電話 → 事務所 → 赤伝** と、人を3回経由しています。

出典: https://www.infomart.co.jp/asp/yougo/akakuroshori.asp ／ https://hachimenroppi.com/faq/000001013/

TOYO LINK は**既に写真付きの返品フローを実装済み**（報告 → 承認 → 精算控除まで通っている）。既存資産がそのまま効きます。出力は「赤伝の元データ（CSV）」で十分。

**注意**: 卸同士では「明日の取引に響くから言わない」という力学が働き、記録すること自体が嫌われる可能性があります。**飲食店⇄卸のほうが機能として刺さりやすい。**

**確信度：中**

### C. 通い箱・コンテナの多段階貸借台帳 ★最も空きが大きい

農畜産業振興機構の2013年調査が、課題をこう名指ししています。

> 「さらなる普及に向けて**滞留するコンテナを把握し、速やかな回収とリユースを促す必要**があり、電子タグを活用したコンテナ管理技術が確立されつつある」

出典: https://vegetable.alic.go.jp/yasaijoho/senmon/1305_chosa01.html

それから十年以上、RFID は工場・物流の**汎用ソリューション**として商品化されましたが、
**産地⇄市場⇄仲卸の多段階を跨いで「誰が何箱持っているか」を台帳化する軽量アプリは見つかりませんでした。**

そして **TOYO LINK の「貸し借りを記録して月末に精算する」構造が、通い箱の貸借にそのまま流用できます。** 品目を「箱」に置き換えるだけです。

**確信度：中**（空白であることは中〜高／事業になるかは未検証）

## 6. ギルド機能の実装コスト評価

「自分ではできない仕事を、できる人に頼む（募集 → 交渉 → 成約 → 作業報告 → 完了確認 → 報酬）」という構想について。

### 結論：新規構想ではなく、**既に約7割できている**

| 分類 | 内容 |
|---|---|
| **そのまま使える** | relay 投稿（`bring` / `need` / `consult`）が **募集 → 引受 → 合意** まで実装済み（`mkRelay` / `submitRelay` / `confirmRelay` / `renderRelayCard`）。seed に「夕方の人手が足りません。2時間だけ手伝える方いませんか」という、まさにギルド案件が入っている |
| **そのまま使える** | 案件スレッド（`messages` / `openChat` / `sendMsg`）、限定公開（`visibleTo` / `canSee`）＝指名依頼に転用可、画像の端末内縮小→base64（`onPhoto` / `onClaimPhoto`）、マイページ3段レイアウト（`renderInbox`）、通知バッジ配線（`incomingConfirm`） |
| **改造すれば使える** | 返品の承認／却下フロー（`submitClaim` / `approveClaim` / `rejectClaim` / `pendingClaimsForSeller`）を、**完了確認・差し戻しに転用**できる。対象を `dealId` → `postId`、宛先を `d.sellerId` → `p.companyId` に変えるだけ |
| **決定的** | **`confirmRelay()` に `state.deals.push()` を足すだけで、既存の月次精算エンジン（`pairGroups` / `lineRow` / `dealNet` / `closeMonth` / `exportDeals`）が無改造で動く** |

### 足りないのは3つだけ

1. 金額フィールド（依頼側の予算／応札側の見積／合意額）— relay の全フィールドに金額項目がゼロ
2. 作業完了報告（実施内容・before/after写真）— 保存する配列も関数も UI も無い
3. 完了確認・差し戻しの relay 版

その他、複数応札（現状 `responderId` は単数スカラで、2社目は `p.status!=='open'` で弾かれる）、作業種別マスタ、評価（`thanks` は 0/1 カウントのみ）、支払・入金記録は新規。

**確信度：高**（コードで確認済み）

### ただし「作るのは安いが、売れるかは別」

飲食店のバックオフィス代行として外に売るのは**筋が悪い**:

- 個別作業は既に専業で埋まっている（撮影・グルメ媒体更新・スポット料理人／シェフリンク等）
- ココナラ・ランサーズにも飲食店向けの出品が実在する（「食べログ、ぐるなび、ホットペッパー運用代行します」等）
- 空いているのは「**束ねる層**」（供給はあるのに飲食店に届いていない探索コスト）だが、卸向け TOYO LINK との接続が弱い
- 「予約台帳の設定代行」は単体サービスが見当たらないが、**市場規模が小さく単体事業にはならない**

**一方で、「卸同士の人手・配送の融通」として既存 relay 機能を完成させるのは極めて安い。**
ギルドは新規事業ではなく、**TOYO LINK の未完成機能の完成**として扱うべき。

**確信度：中〜高**

## 7. 既知の課題（コードは未修正）

検証中に見つかった実際の不具合。**デモを対外的に見せる前提だと、1番は指摘されると痛い。**

| # | 内容 | 該当箇所 |
|---|---|---|
| 1 ★ | **案件チャットに閲覧制御が無い。** 第三者が掲示板から他社同士の価格交渉を全文読める（1対1ではなく公開スレッド）。`guide.html` の「取引の明細は、ご本人と運営しか見られません」と矛盾する | `openChat` / `renderChat` / `messagesOf` / `interestBar` |
| 2 | 返品を**却下**しても「返品 却下（**−¥800**）」と金額が併記され、控除されたように読める | `renderInbox` |
| 3 | CSV が返品控除**前**の `d.amount` を出力。画面の精算は `dealNet()`（控除後）で、**金額が一致しない** | `exportDeals` vs `pairGroups` |
| 4 | **過剰成立が可能。** qty=30 の掲示に2社が30個ずつ申し込み、両方を承認できる（残数も status も再検証していない） | `confirmDeal` |
| 5 | relay を**取り下げても** `status='done'` になり、実績件数と「最近成立・調整したもの」に混入する | `closePost` / `myHelpCount` |
| 6 | 返品却下後、**再申請・異議申立てができない**（ボタンが二度と出ない）。却下理由の入力欄も無い | `myClaimOnDeal` |
| 7 | 締め後に返品が承認されると、**確定済み月の集計額が黙って変わる**。締め済み月の日付で新規取引も追加できる | `closeMonth` は boolean 保存のみ |

### 仕様として認識しておくこと（バグではない）

- `respMin`（応答の速さ）と `verified`（実名確認）は **seed のハードコード値**。実測・運営確認のロジックは存在しない
- 「✅ 精算クリーン」は `closingNeeded()` だけで判定しており、**自己申告のチェックボックスと同義**。支払実績とは無関係
- `TODAY = '2026-06-23'` / `CUR_MONTH = '2026-06'` がハードコード
- 未締め月による投稿ブロックは **求む／出す のみ**。相談・「応じる」・再掲は素通りする
- ログインはロール切替セレクトのみ。すべての制御は**描画時の出し分けであり、アクセス制御ではない**

## 8. 未確認事項（わからないこと）

1. **豊洲で TANOMU の仲卸間機能がこの6年でどこまで普及したか。**

3. 調査時、外部サイトの直接取得がブロックされていたため、**各社の公式「機能一覧」ページを1行ずつ突き合わせてはいません。** 複数ソースの一致で判定しています。

## 9. 次に検討すべき論点（結論は出していない）

- **着手順**：「青果卸の欠品・代替」を主軸にする案が出たが、**自分自身が当事者である案件（デリバリー食材仲介の月末エラー・変更履歴）のほうが、他社の協力なしに明日から測れる。** 立ち上がりが早いのは後者では。
- **「入力は誰がやるのか」問題**：検討の結論が「受付担当が整理する」＝自分の工数に落ち着いており、**音声 → 要約 → 起票 / FAX画像 → OCR → 起票**という「入力を人にさせない」選択肢が一度も検討に出ていない。クロスオーダーの FAX-OCR が精度98%で商用化されている以上、ここは埋めるべき。
- **最初の MVP の形**：全案が「アプリを作る」前提になっているが、**スプレッドシート＋フォームで足りる可能性**がある。普段の道具（Google）に合わせるのが最短。
- **TOYO LINK 本体をどうするか**：横展開の検討ばかりで、既存のデモを続けるのか、型紙として使って別物を作るのかを決めていない。3-1（TANOMU の件）を踏まえると避けて通れない。

## 10. 共通の検証基準

どの案を試すにせよ、判断基準はこれで統一する。

- ❌ 「アプリを使ったか」
- ✅ **確認の往復が減ったか／未完了が減ったか／以前は成立しなかった仕事が成立したか**
